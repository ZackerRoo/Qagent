# Qagent Full-Market Walk-Forward Validation Design

## Goal

Build a reproducible A-share historical replay that answers whether Qagent's complete recommendation process produced useful Top 5 and Top 10 portfolios after realistic trading constraints and costs.

This is the M2 validation engine from `GOALS.md`. It is separate from recommendation follow-through: follow-through measures recommendations generated by the running product, while walk-forward validation reconstructs historical decisions from point-in-time evidence.

## User Outcome

From the existing Backtest page, a user can:

1. choose a historical date range, rebalance interval, Top 5 or Top 10 portfolio, capital, costs, and risk limits;
2. start a background historical replay without blocking the API or browser;
3. see preparation, running, blocked-data, failed, and completed states with progress;
4. compare Qagent with CSI 300, CSI 500, ChiNext, STAR 50, and an equal-weight eligible-universe benchmark;
5. inspect annualized return, excess return, win rate, maximum drawdown, Sharpe, Calmar, turnover, consecutive losses, and cost sensitivity;
6. inspect each rebalance decision, selected instruments, rejected candidates, fills, exits, and rule-based skip reasons;
7. see train, validation, and embargoed out-of-sample results without hiding negative results or replacing missing real data with fixtures.

## Scope

### Included

- A-share exchange-listed stocks and ETFs already supported by Qagent.
- Historical universe reconstruction on every rebalance date.
- The same ranking, factor, strategy, data-quality, and risk-gate semantics used by live daily scans.
- Top 5 and Top 10 portfolio replay.
- Cache-only historical market, fundamental, industry, membership, lifecycle, and tradability evidence from SQLite.
- Raw executable OHLC, adjusted research OHLC, corporate-action metadata, and provider-scoped universe manifests required by historical replay.
- A-share execution constraints, benchmarks, cost sensitivity, chronological validation, deterministic replay, persistence, API, and Backtest-page presentation.

### Excluded

- Live brokerage orders.
- Intraday or tick-level fills. M2 uses daily bars and labels fill precision accordingly.
- Automatic changes to live factor or strategy weights. That belongs to M3.
- Machine-learning factor discovery or Qlib/WorldQuant-scale factor libraries.
- US stocks.
- Synthetic data or fixture fallback in a `free` data run.

## Approaches Considered

### 1. Persisted cache-only walk-forward engine (selected)

Create a dedicated replay engine and background job. It reads only historical SQLite evidence, invokes the live ranking path with an explicit decision date, persists decisions and results, and resumes after process restarts.

This requires more structure, but it protects the API from long runs, makes results auditable, and prevents accidental network or current-date fallback.

### 2. Extend the current synchronous portfolio backtest

This is smaller initially, but the current endpoint accepts a fixed instrument list, returns only after completion, does not persist results, and does not reconstruct the historical universe. Extending it would preserve the main correctness and operability problems.

### 3. Delegate replay to Qlib or another external engine

This provides mature research utilities, but Qagent's live ranking and risk semantics would need a second implementation. Divergence between live and backtest behavior would undermine the main purpose of M2. External engines remain optional future research adapters.

## Architecture

### Module boundaries

`backtesting/walk_forward_models.py`

- Owns versioned request, run status, rebalance, selection, fill, trade, curve, benchmark, metric, validation-window, and result models.
- Contains no database or provider logic.

`backtesting/historical_universe.py`

- Reconstructs the eligible universe as of a decision date.
- Applies listing, delisting, asset-type, suspension, ST, liquidity, and evidence-coverage rules.
- Returns included instruments and explicit exclusion reasons.

`backtesting/replay_provider.py`

- Implements cache-only market and strategy data interfaces over SQLite.
- Enforces `evidence_date <= decision_date` for every lookup.
- Has no network fallback and raises a typed evidence error when a required range is absent.

`backtesting/walk_forward.py`

- Orchestrates preflight, trading sessions, universe reconstruction, historical scans, Top N selection, execution, benchmarks, validation windows, progress, and persistence checkpoints.
- Does not duplicate factor or strategy formulas.

`backtesting/execution.py`

- Extracts the reusable daily-bar execution rules currently embedded in `backtesting/portfolio.py`.
- Models fills, rejected orders, T+1, limits, costs, position sizing, and exits.
- Keeps the existing portfolio endpoint behavior compatible.

`backtesting/metrics.py`

- Computes portfolio, benchmark, excess, drawdown, risk, turnover, trade, and cost-sensitivity statistics from persisted curves and trades.

`jobs/walk_forward.py`

- Runs and resumes a persisted replay job in the historical-data executor.
- Updates phase, progress, heartbeat, current decision date, and error state.

The API and repository remain thin adapters. The frontend consumes persisted result models and does not calculate investment metrics.

## Point-In-Time Data Rules

Every run starts with a data preflight. A real-data run never calls AKShare, BaoStock, Tushare, or another network provider during replay.

For decision date `D`:

- price and volume inputs end at the close of `D`;
- the earliest possible entry is the next valid trading session after `D`;
- fundamentals use the latest publication/as-of row whose date is `<= D`;
- industry uses the latest snapshot whose date is `<= D`;
- index membership uses the latest ready snapshot whose date is `<= D`;
- listing and delisting state are evaluated as of `D`;
- suspension, ST, and price-limit status use the row for the applicable trade date;
- current catalog membership, current fundamentals, and post-`D` bars cannot affect ranking or eligibility;
- raw OHLC prices drive executable prices, limits, stops, and targets; adjusted OHLC drives continuous return and trend features only;
- displayed current names may come from the catalog, but labels cannot affect scoring.

If an as-of snapshot is missing or stale beyond its source cadence, the instrument is excluded with a reason. The engine does not substitute the latest current snapshot.

### Raw and adjusted price prerequisite

The current free A-share cache is not sufficient for execution replay: AKShare requests use `qfq`, and the stored OHLC cannot be treated as raw exchange prices. M2 therefore adds a replay-specific historical bar store containing, for each provider, instrument, and trade date:

- raw open, high, low, close, volume, and turnover;
- adjusted open, high, low, close;
- adjustment factor and adjustment mode;
- corporate-action effective date and source revision where available;
- source provider, fetched time, and dataset revision.

Backfill fetches raw and adjusted series separately, reconciles dates, and derives the factor only when both sides are present. A row without raw OHLC cannot participate in fills or price-limit checks. Splits and distributions change adjusted research series only from their effective date; cash, quantity, and raw execution remain in exchange-price units. If a corporate action changes share quantity or pays cash and the action cannot be represented, a position crossing that action is unresolved and the affected result is blocked rather than approximated.

## Dataset Completeness and Coverage Policy

Historical absence is meaningful only when the source snapshot is known complete. Add provider-scoped universe snapshot manifests with snapshot date, source revision, status (`ready`, `partial`, `failed`), expected count, stored count, error, and fetched time. Historical universe rows include provider mode and revision. The repository exposes as-of readers for universe, lifecycle, tradability, industry, index membership, fundamentals, and replay bars; aggregate statistics are not used for decisions.

Preflight evaluates every rebalance date and uses the complete provider manifest as the denominator. It blocks the run when any of these conditions fail:

- the universe manifest is not `ready`, expected count is unknown, or stored count differs from expected count;
- any expected instrument lacks lifecycle identity, so unknown or delisted instruments could disappear from the denominator;
- exact-date tradability coverage is below 100% for otherwise eligible instruments;
- at least 95% of otherwise eligible instruments do not have the required raw and adjusted lookback sessions;
- stock industry coverage is below 95%;
- stock point-in-time fundamental coverage is below 90%;
- required benchmark session coverage is below 98%.

Recent IPOs with fewer than the configured minimum lookback sessions are rule-based exclusions, not missing-data exclusions, but they remain in the denominator and exclusion report. ETF fundamentals and stock-industry classification are not required for ETFs. Missing ETF classification or trading-rule metadata blocks that ETF rather than the whole run unless aggregate bar coverage then falls below 95%.

Maximum as-of staleness is explicit: 100 calendar days for industry and index membership snapshots; 190 calendar days for fundamentals; exact-session rows for tradability and bars. Universe membership has no stale-snapshot allowance: it is derived for exact decision date `D` from a complete provider-scoped lifecycle inventory, then persisted as an exact-date replay snapshot. Coverage thresholds and staleness limits are persisted in the request and result, not hidden settings.

## Historical Universe Reconstruction

The default scope is Qagent's combined tradable A-share stock and ETF universe. The run records the asset mix so results cannot silently change when ETF availability changes. Its denominator comes from the ready historical universe manifest, never the subset for which bars happened to download successfully.

On each rebalance date:

1. load the ready provider-scoped lifecycle inventory revision and derive all instruments whose listing date is `<= D` and whose delisting date is absent or `> D`;
2. merge lifecycle additions through `D`, including IPOs and newly listed ETFs after the previous materialized snapshot, and materialize an exact-date replay snapshot with expected and stored counts;
3. exclude suspended, ST, missing-bar, stale-evidence, and insufficient-liquidity instruments;
4. apply the same no-chase, volatility, data-quality, and risk blockers used by the live scan;
5. record every included and excluded count by reason;
6. rank the eligible set through the versioned live recommendation path;
7. persist the Top 5 and Top 10 selections plus a bounded rejected-candidate audit list.

Universe snapshots are never backfilled from today's catalog inside a replay. If the required historical universe is unavailable, the run becomes `blocked_data` and returns a coverage report.

## Ranking Compatibility

The historical engine must not reimplement strategy formulas. Before replay, the current daily scan is split into data assembly and a pure `rank_opportunities(context, policy)` contract. `ReplayRankingContext` supplies the decision date, complete instrument identities, bars, point-in-time fundamentals, industries, memberships, tradability, enhanced evidence, and calibration state. The pure ranker cannot construct providers, read `date.today()`, read the current catalog for trading inputs, or query recommendation history itself.

Current-only enhanced evidence such as live fund flow, Dragon-Tiger activity, and cache-TTL snapshots is disabled unless a point-in-time historical adapter passes the same as-of rules. Recommendation-feedback calibration is frozen at neutral for M2; it is neither rebuilt from today's recommendation history nor recursively optimized during replay.

This is not a backtest-only policy. M2 introduces `validated_core_v1` as an actual versioned live policy and makes it the default policy for ranking and risk gating on Today, full-market scans, briefs, paper-candidate intake, and historical replay. Current-only enhanced data and feedback may remain visible as annotations, but cannot change rank, entry state, or risk gates under this policy. A user-selected experimental policy is labelled unvalidated and is not compared with `validated_core_v1` results. Point-in-time adaptive calibration belongs to M3.

Static `KNOWN_CONTEXT` industry and membership values are display fallbacks only and are prohibited from replay scoring. Every included ranking input identifies its source date. A dependency that lacks a historical adapter is explicitly disabled in the policy manifest rather than silently using current data.

Each run persists:

- ranking version;
- strategy and factor version;
- risk-gate version;
- execution-model version;
- request configuration;
- data revision fingerprint;
- mandatory code revision, policy manifest, and ranking-source digest.

A replay fails if a ranking dependency attempts to read the wall-clock date, current feedback, static context for scoring, or a network provider. Tests cover these boundaries.

## Portfolio and Execution Semantics

### Decision and entry

- Decisions are formed after the rebalance-date close.
- Orders are valid for the next trading session only. A missed order expires; a later rebalance may create a new order if the instrument is selected again.
- A buy is skipped when the instrument is suspended, opens at the applicable limit-up, has no valid volume, breaches the no-chase threshold, or would violate cash, liquidity, risk, or position limits.
- No-chase is exact: skip when raw open is above the target or above `trigger_price * (1 + no_chase_pct / 100)`.
- Intended notional and open-fill capacity use only information available at the decision close: the configured participation rate multiplied by the lower of previous-session raw turnover and median raw turnover of the previous 20 sessions. Execution-session total volume never changes an open-order quantity because it was not known at the open; the session must only report positive trading status and volume for the fill to remain valid.
- Entries use the raw next-session open plus configured adverse slippage. A slipped price is capped at the exchange price limit; if the capped price is not executable, the order is skipped.
- A-share quantities use the instrument's versioned board-lot rule and round down. Price limits and prices use the versioned tick size with decimal half-up rounding.

### Position management

- Default maximum positions equals the selected Top N, configurable up to 20.
- Position size is constrained by risk per trade, available cash, maximum position weight, and daily liquidity participation.
- Existing positions are not duplicated on rebalance.
- Sell eligibility respects the versioned settlement rule. Stocks are T+1. ETFs are conservatively T+1 unless historical security metadata explicitly marks the product T+0; newly entered positions are never exited from the same daily bar even when T+0 is allowed.
- Suspended holdings remain marked but cannot be sold.
- Limit-down sessions may prevent a planned stop or rebalance exit.

### Versioned A-share rules

`AShareTradingRuleSet` is effective-dated and persisted with the run. It covers regular main-board 10%, ST 5%, ChiNext/STAR 20%, Beijing Stock Exchange 30%, tick size, board lot, and effective-dated IPO no-limit windows. Historical rule changes are separate schedule rows. ETF price-limit, lot, settlement, and fee rules come from product metadata; an ETF with unknown applicable rules is excluded. Tests cover both sides of every effective-date boundary used by the requested range.

Fees are also effective-dated: commission and minimum commission come from run configuration; stock sell-side stamp duty and transfer fees use the schedule applicable to the trade date and exchange; ETFs do not inherit stock stamp duty. Every fee component is stored separately.

### Exit order

Every session follows one causal event sequence:

1. apply supported corporate actions effective before the open;
2. mark suspension, exchange limits, and tradability for the session;
3. process gap-through protective stops for positions held before the session;
4. process pending time and rebalance exits created at the prior close;
5. fill next-session entry orders in persisted rank order using only cash and slots actually released;
6. evaluate intraday stop then target touches for positions held before the session;
7. mark all positions at raw close, calculate equity, and generate time/rebalance orders for the next session;
8. atomically persist events and the end-of-session checkpoint.

Rebalance replacement sells instruments no longer selected before buying replacements. A blocked or partially filled exit keeps its position slot and prevents over-allocation.

Stop and target behavior is exact:

- if the raw open is at or below a long stop, fill at raw open minus adverse slippage, subject to the lower price limit and liquidity;
- otherwise, an intraday stop touch fills at the stop minus adverse slippage;
- if the raw open is at or above a target, conservatively fill at the target minus sell slippage;
- otherwise, an intraday target touch fills at the target minus sell slippage;
- when one daily bar touches both stop and target and order is unknowable, stop wins;
- time and rebalance exits generated at the prior close run after open-gap protective stops and before new entries, filling at raw open minus adverse slippage when eligible;
- an entry session cannot also produce an exit for that new position.

Stops, targets, time exits, and rebalance exits are evaluated from daily bars. The result exposes the conservative ordering assumption.

Exchange-limit executability is deterministic. A buy-at-open is blocked when raw open equals the effective upper limit; a sell-at-open is blocked when raw open equals the effective lower limit. Adverse slippage is rounded and capped at the applicable limit; the resulting price must lie inside the raw session range and volume must be positive. Intraday stop/target fills require their rounded price to lie inside the raw range and not equal a side that cannot execute. There is no optimistic queue fill at a one-price limit session.

Actual open fill quantity is the minimum of requested quantity, available cash/position, and the prior-known rounded participation capacity above. Intraday protective exits use the same prior-known capacity, so no fill quantity depends on end-of-session volume. Entry remainders expire at the session close. Exit remainders persist with the same purpose and retry each later session until filled, replaced by a higher-priority protective stop, cancelled because the position is gone, or made unresolved by terminal data. Every partial fill and retry is an event.

Exit prices include slippage, commission, transfer fees where configured, and A-share sell-side stamp duty. All costs are persisted separately from gross P&L.

A confirmed suspended holding is valued at its last observable raw close and is exempt from the unexpected-missing-session counter for every session carrying an authoritative suspension row. Reaching the requested end date is normal: open positions are marked to that date's raw close, remain open, and contribute to equity and drawdown; only completed trades contribute to win rate and consecutive-loss metrics. M2 does not force liquidation or read post-range bars.

If a holding has an authoritative delisting cash value, conversion value, or final exchange settlement, the engine settles it on the effective date and records a terminal event. An otherwise trading instrument that lacks both bars and an authoritative suspension/delisting row for five consecutive expected in-range sessions becomes unresolved. A delisting without authoritative terminal value is also unresolved. The engine never invents a zero or last-price liquidation.

### Corporate actions

Replay action rows require instrument, action type, announcement date, record date, ex-date, payable date, cash per pre-action share, split/bonus ratio, rights ratio and subscription price when applicable, previous raw close, exchange ex-right reference price, source, and dataset revision. An action becomes visible to ranking and risk logic only on sessions whose date is on or after its announcement date.

Entitlement is frozen from the position quantity held at the record-date close and persisted as its own event. Split/bonus quantity is applied before the ex-date open from that frozen entitlement; cash dividend is credited on payable date from the same entitlement even if the position was sold after the record date. If an action row arrives too late to reconstruct a required record-date entitlement inside the leased revision, the affected ledger is blocked instead of retroactively changing history.

- cash dividend: credit `pre_action_quantity * cash_per_share` on payable date and record dividend P&L separately; economic trade return includes the cash;
- split or bonus shares: multiply quantity by `1 + share_ratio`, divide per-share cost display by the same factor, and preserve total cost;
- stop and target: multiply raw levels by `ex_right_reference_price / previous_raw_close`, rounded to the new tick, so economic distance is preserved;
- price limits on the ex-date use the authoritative ex-right reference price, not the previous unadjusted close;
- rights issues, mergers, conversions, or actions missing required fields are `unsupported_corporate_action`; if held across the effective date, the scenario/variant becomes `blocked_data` at that session with prior checkpoints preserved.

### Cost sensitivity

The base replay is followed by deterministic low, base, and high cost scenarios using the same ordered selections and market observations. Each scenario independently re-simulates cash, quantities, fills, exits, and later capacity because different costs can change affordable quantity. Scenarios never rerank the universe. Scenario identity is part of every ledger key and result fingerprint.

## Benchmarks

Daily normalized curves are produced for:

- CSI 300 (`CN:000300.IDX`);
- CSI 500 (`CN:000905.IDX`);
- ChiNext (`CN:399006.IDX`);
- STAR 50 (`CN:000688.IDX`);
- equal-weight eligible universe.

CSI 300 is the required primary benchmark. Its adjusted close must cover at least 98% of requested sessions after its inception or the run is `blocked_data`. CSI 500, ChiNext, and STAR 50 are required comparison series only for sessions on or after their inception; a comparison below 98% coverage is marked unavailable but does not block the primary portfolio result. No ETF proxy is substituted for an index.

Index curves use adjusted close-to-close price returns on the intersection of requested trading sessions and the series' valid post-inception dates, forward-fill nothing, and begin at net value 1.0. Excess metrics align exact common sessions and disclose their count.

The equal-weight eligible-universe benchmark is reconstructed at the same rebalance dates, admits constituents only after they pass the identical historical eligibility and coverage rules, weights equally at the next-session open, applies the base fee/slippage schedule and the same blocked-trade rules, and rebalances by selling departures before buying additions. Its turnover and costs are reported; it is not a frictionless cross-sectional average.

## Temporal Validation

Unique rebalance decision dates are split chronologically 50%/25%/25% using floor boundaries: `train_end = floor(N * 0.50)` and `validation_end = floor(N * 0.75)`, with at least one raw decision date per segment or an insufficient result. Embargo is measured in XSHG trading sessions, not rebalance observations: a decision is admitted only when more than `max_holding_sessions` XSHG sessions have elapsed since the previous raw segment's last decision date.

Ranking is computed once, but performance uses four independent ledgers per Top N and cost scenario: one continuous full-period ledger plus train, validation, and out-of-sample ledgers. Every window ledger resets to the configured initial capital, starts with no positions or orders, and accepts only decisions assigned to that non-embargo window. Positions never cross from training into validation or from validation into out-of-sample. A trade is attributed by decision date even if it remains open at the window's requested end; it contributes to window equity but not completed-trade metrics.

Weights and parameters are fixed for the complete run. Training results do not alter validation or out-of-sample weights. M2 measures the current version; M3 will govern weight changes.

The gate applies independently to Top 5 and Top 10 under the base-cost scenario. Each variant remains `insufficient` until its independent out-of-sample ledger has at least 30 completed trades and a complete CSI 300 comparison over the exact sessions from that ledger's first eligible execution session through its window end. With at least 30 trades, deterministic 1,000-sample bootstrap confidence intervals use a persisted seed over net trade returns. `positive` requires the 95% mean-return interval lower bound and exact-session annualized CSI 300 excess to be above zero; `negative` requires the interval upper bound below zero; otherwise the result is `inconclusive`. Negative results and confidence intervals remain visible.

Metric formulas are fixed:

- cumulative return: `ending_net_equity / starting_equity - 1`;
- annualized return: `(ending_net_equity / starting_equity) ** (252 / elapsed_sessions) - 1`;
- cumulative and annualized excess: portfolio return minus the exact-session benchmark return;
- win rate: completed trades with net P&L above zero divided by completed trades;
- maximum drawdown: minimum of `net_equity / running_peak - 1`;
- Sharpe: `sqrt(252) * mean(daily_net_return - daily_risk_free_rate) / sample_std`, with annual risk-free rate defaulting to zero and persisted in the request;
- Calmar: annualized return divided by the absolute maximum drawdown;
- annualized one-way turnover: `(buys + sells) / (2 * average_net_equity) * 252 / elapsed_sessions`;
- maximum consecutive losses: longest sequence of negative-net-P&L completed trades ordered by exit date and event sequence.

Undefined divisions remain null with a reason; they are not rendered as zero.

## Persistence

Add normalized SQLite storage:

### `walk_forward_runs`

- primary key `run_id`; atomically unique `reuse_key`; parent run, provider, status, phase, progress, worker lease, heartbeat, cancellation request, date range, request JSON;
- strategy/ranking/risk/execution versions, data and result fingerprints;
- summary, temporal validation, data health, warnings, error, timestamps.

### `walk_forward_rebalances`

- primary key `(run_id, variant, decision_date)`;
- universe revision, counts, complete ordered-selection fingerprint, and checkpoint status.

### `walk_forward_rankings`

- primary key `(run_id, decision_date, instrument_id)`;
- full eligible-universe rank, scores, policy components, source dates, gate decision, and exclusion reasons.
- Audit storage is complete; API pagination, not persistence truncation, bounds presentation.

### `walk_forward_orders`

- primary key `order_id`, with unique `(run_id, scenario, variant, decision_date, instrument_id, side, purpose)`;
- intent, lifetime, requested quantity, rank order, status, and skip reason.

### `walk_forward_events`

- primary key `(run_id, scenario, variant, event_sequence)`;
- ordered order, fill, skip, fee, corporate-action, and ledger events.

### `walk_forward_trades`

- primary key `(run_id, scenario, variant, trade_id)`;
- instrument, signal and fill dates, quantities, prices, gross/net P&L, fee components, slippage, and exit reason.

### `walk_forward_session_checkpoints`

- primary key `(run_id, scenario, variant, trade_date)`;
- atomic end-of-session cash, positions, pending orders, event sequence, and ledger checksum.
- Recovery resumes after the latest complete session, not only the latest rebalance.

### `walk_forward_equity_points`

- primary key `(run_id, scenario, variant, trade_date)`;
- cash, market value, gross and net equity, drawdown, turnover;
- benchmark values and excess values for all required benchmarks.

Repository writes for one session are atomic and idempotent by the keys above. A completed session checkpoint is not recalculated during restart recovery. Cost scenarios have independent checkpoints and ledgers.

## Determinism and Recovery

Historical writes increment a monotonic `historical_data_revision`. A persisted dataset lease prevents historical backfill or cache replacement while a walk-forward run owns a revision; backfill and replay are mutually exclusive. The engine verifies the revision before every checkpoint and at completion. A changed revision fails the run as an integrity error.

The request fingerprint combines normalized configuration, mandatory code/policy/version identifiers, and the leased data revision. Code revision is the Git commit plus a digest generated from a committed replay dependency manifest, or a packaged source digest when Git metadata is unavailable. The manifest covers every replay-affecting source: ranking, factors, strategies, risk gates, providers, universe construction, execution, corporate actions, metrics, temporal splitting, calendars, persistence serialization, schema/migrations, configuration defaults, Python version, and locked dependency versions. It is never optional.

`reuse_key` is the request fingerprint for normal runs and the request fingerprint plus a random force nonce for forced runs. Creation occurs in one SQLite transaction under the unique constraint: concurrent normal requests either insert once or select the existing row. This applies to queued, preflight, running, and succeeded runs; obsolete results cannot be reused after a replay dependency or data revision changes.

All hashes use SHA-256 over UTF-8 canonical JSON: sorted object keys, ISO dates, explicit nulls, fixed-scale decimal strings, and arrays sorted by deterministic semantic order. Before result hashing, records are projected to semantic fields and exclude run id, parent id, UUIDs, database sequence keys, creation/update times, worker/lease metadata, and force nonce. Event identity inside the projection uses deterministic scenario, variant, session, instrument, purpose, side, and local ordinal fields. The result fingerprint covers the full ordered rankings, selections, orders, events, trades, checkpoints, curves, and metrics. Two forced runs with identical evidence and semantics must produce equal result fingerprints.

Status transitions are `queued -> preflight -> running -> succeeded`, with terminal alternatives `blocked_data`, `failed`, or `cancelled`. In one immediate SQLite transaction, a worker verifies the current historical revision and either inserts a five-minute dataset lease for its run or reenters the unexpired lease already owned by that same run. Another run cannot take the lease. The worker updates heartbeat at least every 30 seconds and after each session.

A lease with no heartbeat for ten minutes is stale. Startup recovery may atomically take over a stale lease only for its original recoverable run id and unchanged historical revision. A stale lease whose owner is terminal is cleared before normal acquisition; a stale lease owned by a different nonterminal run keeps newer runs queued until recovery resolves it. Every terminal transition releases the lease in `finally`, and startup cleanup releases orphaned terminal leases.

`cancel_requested_at` is idempotent. The worker checks it before each session transaction, commits no partial session, releases the dataset lease, and enters `cancelled`. Completed runs cannot be cancelled. Any unsupported corporate action or unresolved terminal value in a requested Top N or cost-scenario ledger moves the whole run to `blocked_data`; unaffected checkpoints remain inspectable, but no requested portfolio is presented as a completed result.

## API

### `POST /api/walk-forward/runs`

Starts or reuses a run. Request fields include provider, date range, rebalance sessions, Top N variants, asset scope, initial capital, maximum positions, risk per trade, maximum position weight, liquidity participation, no-chase threshold, holding horizon, effective-dated fee/rule schedule versions, slippage, coverage thresholds, staleness limits, risk-free rate, and `force`.

Returns the persisted run summary immediately.

For an identical request and revision, a queued/running/succeeded run is reused. A blocked, failed, or cancelled run is returned with its remediation unless `force=true`; force creates a new run with `parent_run_id` and never mutates the old audit record.

### `GET /api/walk-forward/runs`

Lists recent runs without large curves or trade payloads. Parameters are `provider`, `status`, `limit` (1-100), and opaque cursor, ordered by creation time and run id descending.

### `GET /api/walk-forward/runs/latest`

Returns the latest run summary for the selected provider.

### `GET /api/walk-forward/runs/{run_id}`

Returns summary, status, coverage, metrics, temporal windows, cost scenarios, and bounded chart data. Trades and rebalance details are paginated or requested separately.

### `GET /api/walk-forward/runs/{run_id}/rebalances`

Returns paginated rebalance decisions and exclusion summaries with `variant`, date range, `limit` (1-200), and opaque cursor filters.

### `GET /api/walk-forward/runs/{run_id}/trades`

Returns paginated fills, skipped orders, exits, and costs with scenario, variant, instrument, status, date range, `limit` (1-500), and opaque cursor filters.

### `POST /api/walk-forward/runs/{run_id}/cancel`

Requests cooperative cancellation.

## Backtest Page Design

The existing Backtest navigation gains an independent `历史回放` tab containing `全市场滚动验证`. Recommendation follow-through remains in a separate `推荐跟踪` tab with separate requests, state, terminology, and verdicts. Their sample counts and charts are never merged.

### Primary view

- compact run controls and one start button;
- current phase, progress, date, elapsed time, and evidence coverage;
- a verdict strip that distinguishes historical backtest from recommendation follow-through;
- a net-value line chart for Top 5, Top 10, and selected benchmarks;
- a separate drawdown chart;
- a compact metric table with net/gross values and benchmark excess;
- train, validation, and out-of-sample cards;
- cost sensitivity comparison.

### Drill-down

- rebalance timeline with universe, eligible, selected, and rejected counts;
- Top selections with recommendation reason, entry plan, and ranking components;
- trades and missed orders with plain-Chinese reasons;
- a data-reliability drawer showing missing or stale evidence.

Empty charts are not rendered. A blocked run shows the exact missing coverage and the backfill action required. Long diagnostic payloads remain behind progressive disclosure.

## Error Handling

- `blocked_data`: primary benchmark, universe completeness, raw execution prices, corporate-action handling, or declared coverage thresholds are incomplete; no partial performance claim is emitted. An optional post-inception comparison benchmark below 98% is unavailable but does not block the primary result.
- `failed`: code, storage, or invariant failure; preserve the last checkpoint and a concise operator error.
- `cancelled`: preserve completed checkpoints but do not label the run complete.
- individual instrument evidence gaps: exclude the instrument and count the reason; fail the run under the explicit completeness and coverage policy above.
- network access attempt during replay: fail immediately as an integrity error.
- zero trades: return a real zero-trade result with eligibility and blocking reasons, never sample values.

## Verification

### Unit tests

- as-of queries reject future bars, fundamentals, classifications, memberships, and lifecycle state;
- historical universe reconstruction includes delisted historical instruments and excludes not-yet-listed instruments;
- ranking uses only the explicit decision date;
- daily execution covers T+1, suspension, limit-up entry, limit-down exit, no-chase, lot size, costs, liquidity, and conservative same-bar stop/target ordering;
- metrics cover annualized return, excess, drawdown, Sharpe, Calmar, turnover, consecutive losses, and cost scenarios;
- identical inputs produce identical result fingerprints.

### Integration tests

- a synthetic but explicitly fixture-labelled historical dataset completes end to end;
- a free-data run with missing coverage becomes `blocked_data` without fixture fallback;
- restart recovery resumes after the latest completed session checkpoint without duplicate orders, events, or trades;
- Top 5 and Top 10 use identical rankings but independent ledgers;
- optional post-inception comparison-benchmark gaps downgrade only the affected comparison and remain visible;
- out-of-sample validation requires 30 completed trades for a validated label.
- mutable data revisions cannot change during a leased replay;
- session-level recovery preserves cash, positions, orders, and event order;
- current-only enhanced data, static context, and recommendation feedback cannot enter replay ranking.

### Product verification

- full backend suite and Ruff pass;
- frontend contract checks and production build pass;
- desktop and narrow-screen browser journeys start a run, monitor progress, inspect curves, open a rebalance, inspect a skipped fill, and reload without losing state;
- no page shows indefinite loading, horizontal overflow, fixture values in a free run, or an empty chart presented as evidence;
- a final roadmap audit and code review have no unresolved high-severity correctness issue.

## Definition of Done

M2 is complete only when:

- the validated historical dataset covers the requested full-market scope and the preflight passes;
- two identical runs produce identical selections, fills, trades, curves, and metrics;
- no decision reads future evidence;
- Top 5 and Top 10 results include all required metrics and benchmark comparisons;
- out-of-sample evidence contains at least 30 completed trades before a validated label is possible;
- negative and zero-trade results remain visible;
- persisted jobs survive backend restart;
- automated and browser verification pass.
